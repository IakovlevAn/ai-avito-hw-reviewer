# План проверки гипотез и качества

## Что проверяем к финалу

### H1. Предварительное ревью экономит действия ревьюера

Метрика: число ручных шагов от открытия работы до готового черновика обратной связи.

Предварительный критерий успеха: система сама собирает доказательства и готовит предложения по всем формально проверяемым критериям; человек работает с единым экраном.

### H2. Разбалловка соответствует уровню решения

Метрики:

- корректный порядок итогов: хорошее > среднее > слабое;
- средняя абсолютная ошибка по критериям относительно эталона;
- доля критических замечаний, найденных системой;
- доля неподтверждённых замечаний.

Предварительный критерий успеха: система сохраняет порядок трёх решений, находит основные нарушения и не маскирует неопределённость высокой уверенностью.

### H3. Отказ снижает риск уверенной ошибки

Метрики:

- доля критериев со статусом `needs_human`;
- точность среди критериев, которые система оценила;
- число уверенных ошибок.

Предварительный критерий успеха: неоднозначные архитектурные выводы чаще уходят человеку, чем получают необоснованный балл.

### H4. Автораспределение делает очередь прозрачной

Метрики:

- доля работ, назначенных без ручного выбора;
- максимальное превышение лимита ревьюера;
- объяснимость назначения по журналу факторов;
- число просроченных неназначенных работ.

Эффект на реальное время методиста можно доказать только пилотом; на хакатоне проверяется корректность логики на моделируемом пуле.

## Набор тестирования

Используются три предоставленных решения одной Go-домашней работы:

- слабое;
- среднее;
- хорошее.

Все три проверяются одной версией рубрики, промптов, моделей и инструментов. Версия исходного кода фиксируется commit SHA.

## Эталон

Команда вручную формирует для каждого решения:

- балл по каждому критерию;
- обязательные замечания;
- допустимые альтернативные реализации;
- критерии, которые нельзя подтвердить статически;
- ожидаемые причины отказа.

Эталон не строится по названию папки «слабое/среднее/хорошее»: оценка сначала выполняется по содержимому, категория используется только для итоговой sanity-проверки.

## Контракт результата AI

Для каждого критерия сохраняются:

- `criterion_id`;
- `status`: `pass`, `partial`, `fail`, `needs_human`;
- `suggested_points` или отсутствие балла;
- `confidence` от 0 до 1;
- текстовое объяснение;
- доказательства: файл, строка, команда или результат теста;
- ограничения вывода;
- черновик обратной связи студенту.

## Уверенность и отказ

Предварительное правило:

- высокая уверенность — критерий подтверждён несколькими согласованными источниками;
- средняя — есть прямое доказательство, но остаётся интерпретация;
- низкая — данных недостаточно, источники конфликтуют или требуется выполнение за пределами безопасного раннера.

Числовой порог будет выбран по результатам трёх работ. До калибровки любое значение порога является гипотезой.

## AI-сигнал

Проверяются только косвенные сигналы: структура истории изменений, резкие несогласованные изменения стиля, сходство с другими решениями, необычные артефакты генерации и способность объяснить решение. Ни один сигнал не считается доказательством и не влияет на балл автоматически.

## Бюджет и производительность

Для каждого прогона фиксируются:

- число модельных вызовов;
- токены и стоимость;
- полное время обработки;
- доля повторных вызовов;
- стоимость одной работы.

Целевой общий бюджет разработки и демонстрационных прогонов — до 3 000 рублей. Точный лимит на одну работу определяется после первого измеренного прогона.
