# Архитектура MVP

## Компоненты

### Web application

Интерфейсы координатора, ревьюера и студента. Авторизация не входит в промежуточный MVP; роли доступны внутри демонстрационного workspace.

### Backend API

Хранит пользователей, курсы, задания, критерии, работы, назначения, запуски проверки, решения ревьюера, уведомления и экспорты.

### GitHub App

Получает события установки и Pull Request, проверяет подпись webhook, фиксирует репозиторий и commit SHA и передаёт работу в очередь.

### Assignment scheduler

Фильтрует ревьюеров по специализации и лимиту, затем ранжирует по текущей очереди, ожидаемому освобождению, SLA и давности последнего назначения. Сохраняет объяснение выбора.

### Sandbox runner

Клонирует только зафиксированную версию репозитория и запускает разрешённый набор команд в одноразовом контейнере без исходящего сетевого доступа, с лимитами CPU, памяти и времени.

### Evidence collector

Собирает структуру проекта, результаты сборки и тестов, статические признаки и точные ссылки на файлы. Отделяет наблюдение от модельной интерпретации.

### Model pipeline

1. Нормализатор задания и рубрики.
2. Специализированный оценщик `task1`.
3. Специализированный оценщик `task2`.
4. Специализированный оценщик `task3`.
5. Критик, ищущий неподтверждённые выводы.
6. Арбитр, объединяющий доказательства и уверенность.
7. Отдельный рекомендательный анализ AI-сигналов.

### Human review

Ревьюер видит доказательства, меняет балл и комментарий, подтверждает отказ и отдельно принимает решение по AI-сигналу. Все изменения журналируются.

### Telegram bot and Excel export

Бот отправляет назначения, напоминания и уведомления о результате. Excel содержит подтверждённые баллы, комментарии, ссылку, статус и сроки.

## Поток данных

`GitHub webhook → ingest → assignment → sandbox/evidence → model pipeline → review UI → approval → student result + Excel + analytics + Telegram`

## Минимальная схема данных

- `users`, `reviewers`, `reviewer_skills`;
- `courses`, `assignments`, `criteria`;
- `submissions`, `submission_versions`;
- `assignments_to_reviewers`;
- `review_runs`, `criterion_results`, `evidence`;
- `human_decisions`, `ai_usage_signals`;
- `notifications`, `exports`, `audit_log`.

## Надёжность и безопасность

- webhook принимается только с корректной подписью;
- секреты хранятся вне репозитория;
- пользовательский код исполняется в изоляции;
- commit SHA делает проверку воспроизводимой;
- модель получает минимально необходимый контекст;
- низкая уверенность приводит к отказу, а не к выдуманному баллу;
- окончательное решение всегда подтверждается человеком;
- повторные задачи идемпотентны по `submission_version + rubric_version`.

## План развёртывания

Для хакатона компоненты разворачиваются в Yandex Cloud. Конкретный набор управляемых сервисов выбирается после проверки доступных квот и цен, чтобы общий демонстрационный бюджет не превысил 3 000 рублей. Архитектура допускает объединение API и worker в одном сервисе на раннем этапе, если это снизит стоимость без потери сценария.
